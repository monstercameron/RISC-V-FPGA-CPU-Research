Built on 2026-11-22 from the research report `build/research/riscv-matrix.md` (ignored, not
committed), section 4. **Goal: the Apple M6 reference, set 2026-11-22 03:37 (an estimate; see "Goal (Apple M6 reference)").** This page records the workload, the checks, a
laptop reference measured the way the other targets pages measure theirs, and the baseline of our
core. The goal section below holds the target the user set.

Everything here is simulation (rubric evidence class E1) or a native laptop measurement. Nothing is a
hardware result of our core, and no clock frequency is claimed.

## Workloads

All kernels are scalar C (no vector unit exists yet), `-O2`, `-ffp-contract=off`. Matrices are stored the
way a weight matrix is, so both operands stream with stride 1: `C[i][j] = sum_k A[i][k] * Bt[j][k]`.

| ID | Kernel | Shape | MACs | Weight bytes | Output check |
|---|---|---|---:|---:|---|
| G1 | int8 x int8 -> int32 GEMM | 64x64x64 | 262,144 | 4 KiB | exact integers |
| G2 | BF16 x BF16 -> FP32 GEMM | 64x64x64 | 262,144 | 8 KiB | bit-exact FP32 |
| G3 | FP32 GEMM | 64x64x64 | 262,144 | 16 KiB | bit-exact FP32 |
| V1 | int8 GEMV -> int32 | R x 2048 | R x 2048 | R x 2 KiB | exact integers |
| V3 | Q4_0-style int4 GEMV -> FP32 (blocks of 32, FP16 scale, int8 activation with an FP32 scale per block) | R x 2048 | R x 2048 | R x 1,152 B | bit-exact FP32 |
| V4 | FP32 GEMV | R x 1024 | R x 1024 | R x 4 KiB | bit-exact FP32 |
| V1b | int8 GEMV larger than the 4 MiB L2 (full profile only) | 4096 x 2048 | 8,388,608 | 8 MiB | exact integers |

Two profiles share one data seed per array (so G1-G3 are identical in both):

| Profile | V1 rows | V3 rows | V4 rows | V1b rows | Retired instructions (hard float) | Mode |
|---|---:|---:|---:|---:|---:|---|
| `small` | 256 | 128 | 256 | none | 14.56 M | **full** on the RTL (from reset), 167 s |
| `full` | 2048 | 2048 | 1024 | 4096 | 136.35 M | **sampled** (the 8 MiB V1b is sampled-only) |

- **Definitions.** BF16 is the upper half of an FP32; its products are exact in FP32, so a fused and an
  unfused BF16 kernel agree bit for bit. `mm_f32_to_bf16` (round to nearest even, carry into the exponent
  correct) makes the BF16 inputs from FP32 values with random sign, exponent 2^-8..2^7 and a full
  23-bit fraction. FP32 inputs have 16-bit fractions in [-1, 1), so every summation order differs in
  the bits. "Ordered" means every output sums its products in ascending k from +0, one rounding per
  addition, no fused multiply-add. The Q4_0 block is ggml's (FP16 scale, 16 bytes, byte j holds weights
  j and j + 16, each minus 8); the FP16 to FP32 step is integer code (`mm_f16_to_f32`), and the
  soft-float build converts the block's integer sum by integer code too (`mm_i2f`, verified against
  the hardware conversion).
- **Checks.** Each kernel's output buffer is hashed (FNV-1a 64) **after the stop marker**, so hashing is
  not timed. `mm_export.sh` builds `mm_native.c` (the same kernel sources and data, `-ffp-contract=off`,
  host clang) and records the mailbox words in `expected.json`; every RV64 run must reproduce them word
  for word on rv_iss, and the RTL timing run must as well. The native build first self-checks
  `mm_i2f` (every |v| to 2^20, powers of two and neighbours), every finite FP16 against `_Float16`,
  BF16 rounding cases (tie to even, tie to odd, above a tie, carry) and an independent 64-bit
  reverse-order recomputation of G1 and V1. Differential traces (RTL against rv_iss, wait cycles
  alternating 0 and 7) check the timed pieces.
- **Limitations.** Each kernel runs once from cold caches and predictors (no warm-up pass); the laptop
  figures are warm medians. The small profile runs 128-256 rows of each GEMV, which stream cold
  weights once per call whatever the row count. The GEMV rows are the same algorithm at a smaller size;
  `full` has the research's shapes. There is no Q4_0 or V1b SIMD reference on the laptop (below).
- **RVV hooks.** `mm_build.py` has a `VARIANTS` table and `--mm-variant`; a later `mm_kernels_rvv.c`
  defining the same functions (built only with `--vector`, once released) is one table entry. No RVV
  kernel is written.

Commands (Linux or WSL for the host steps; the builds ran with the installed clang 23.1.5):

```sh
bash sim/cpu/bench/mm/mm_export.sh small          # or full: build/cpu/bench/mm-data/<profile>/, expected.json
python3 -B sim/cpu/bench/build_bench.py --benchmark mm --isa rv64imfd_zba_zbb_zbs_zifencei   # or rv64im_zba_zbb_zbs_zifencei
python3 -B sim/cpu/bench/run_bench.py --benchmark mm --core ooo --sim verilator --fpu \
    --out-dir build/cpu/bench/mm-small-rv64imfdb            # full mode; soft float: no --fpu, default out-dir
# full profile (--mm-data build/cpu/bench/mm-data/full at build time), sampled, split to stay under 300 s:

bash sim/cpu/bench/mm/mm_laptop.sh small 15 19 > small-run.txt                               # laptop (aarch64)
```

## Laptop measurement (2026-11-22 03:04-03:05)

NVIDIA RTX Spark N1X, one Cortex-X925 (vCPU 19, `taskset`), aarch64 WSL Ubuntu 24.04, Ubuntu clang
18.1.3 `-O2 -fno-vectorize -fno-slp-vectorize -ffp-contract=off`: **the same scalar C, kernels and
data** as the RV64 build (`mm_laptop.c` links `mm_kernels.c` and `mm_data.S`), checked against the same
`expected.json` (every kept run reproduced all checksums). Per clock is by the CPU's own user-space
cycle counter (PMUv3 0x11), as for rt and JS. Each run ramps the clock for 0.4 s, probes the core's
peak (8 independent add chains, 7.8-7.96 instructions per clock when healthy), then times each kernel
as the median of 7 trials of back-to-back calls. 15 runs per profile; **runs whose probe is below 0.9 x
the median probe are dropped** (3 of 15 for `small`, 1 of 15 for `full`: the vCPU shared a core or moved),
and the table is the median over the kept runs with the min-max. Load average was 11-13 of 20 vCPUs from
other work, which shows as the long tails, not the medians (the two profiles' G1-G3 medians agree
within 1.5%).

## Goal (Apple M6 reference, set 2026-11-22 03:37)

The user decided "M6 everywhere": goals are referenced to Apple's M6 core per clock, single thread. Apple
publishes no M6 microarchitecture or matrix figures, so each goal is a **bridge or a different-chip figure, an
estimate and not a measurement**. Source: `build/research/performance-targets.md` (ignored, not committed; Notebookcheck M6 and RTX Spark analyses, fetched 2026-11-22).

**Scalar kernels: 1.30 x the laptop's MAC/clk** (the table above, unchanged), the Geekbench 6 single-core
per-clock ratio M6 / X925 (983 / 755; M6 4,698 at 4.78 GHz, laptop 3,096 at 4.1 GHz, Notebookcheck). The report

### What the first numbers say

- **In flat memory our scalar MAC/clk is above the laptop's on every kernel but the FP32 GEMV.** The
  wide front end runs the simple loops at IPC 7-15 against the X925's 3-6. The FP32 GEMV (V4) is one
  serial FADD chain per output (2 clocks per element, at most 0.5 MAC/clk; measured 0.41) and sits below
  the laptop (0.52). RISC-V needs 1.0x (G2, G3, V3) to 1.4x (V1) the AArch64 instructions.
- **A GEMV in the deciding configuration is latency-bound, not bandwidth-bound.** V1 reaches 0.164
  B/clk, 2% of the SoC's 8 B/clk DRAM ceiling and 16% of the flat-memory rate, because each cold
  64-byte line costs 350 clocks and the core has no hardware prefetcher; four misses in flight cover
  only part of it. This is the figure a streaming-prefetch or deeper miss-parallelism change would move,
  and the part of mm that the in-L1 7-Zip, rt and JS workloads do not exercise.
- **Soft float costs 11x (V4) to 27x (G3) on the FP32 kernels** (0.036-0.039 against 0.41-0.97 MAC/clk) at 41-42
  million instructions per 262,144-MAC kernel, about 160 per MAC. V1 and G1 are unaffected, and V3 loses
  4.7x (0.413 against 1.929) to the soft FP32 scale multiply and add per block.
