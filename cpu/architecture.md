# CPU architecture, version 0.14.3

Versioned with [semantic versioning](https://semver.org/); rules and history are in section 9. "Revision 0" in this document is version 0.1.0.

Decision date: October 23, 2026. User priority: **CPU core first**. This design starts a programmable FPGA processor and keeps RVA23 as a tracked destination. It supersedes the previous accelerator-first priority, while preserving the old accelerator contracts as historical/future-work references.

## 1. Target and first implementation

Long-term target: little-endian **RVA23U64**, including its mandatory scalar, vector and execution-environment behavior. Full RVA23S64 is a separate later project scope: it adds supervisor, virtual-memory and hypervisor requirements. A CPU with RV64I plus a vector MAC is insufficient to claim either profile. [RVA23 specification](https://github.com/riscv/riscv-profiles/blob/main/src/rva23-profile.adoc).

The implemented foundation is an RV64I instruction execution engine, plus local FENCE.I semantics, since 0.4.0 the M extension and since 0.6.0 the B extension (Zba, Zbb, Zbs; ISA string `rv64im_zba_zbb_zbs_zifencei`), with a terminal laboratory execution environment. Its supported operations are tested but not ISA-certified. No A/C/F/D/V, CSR instructions, contained privilege traps, interrupts or MMU are implemented; instruction and data caches were added in 0.2.0 and 0.3.0. Unsupported operations trap; hardware capabilities are not falsely advertised through a fabricated `misa` CSR.

| Choice | Revision 0 decision | Reason |
|---|---|---|
| RTL language | Synthesizable SystemVerilog constructs | Clear state and bit widths; current Icarus simulation route |
| Integer width | XLEN=64 from the beginning | Avoid rebuilding the datapath after an RV32-only prototype |
| Execution | One instruction at a time, multicycle | No speculation, hazard forwarding, reorder buffer or branch predictor needed |
| Register file | 32 x64, combinational reads, one sequential write; x0 reads zero | Simple initial implementation; synthesis must measure mux/register cost |
| ALU | Add/subtract, shifts, comparisons, bitwise, RV64 word operations | A complete useful base arithmetic path |
| Memory port | Unified 64-bit, byte strobes, one outstanding transaction | Compatible with simple synchronous RAM and later adapters |
| Instruction cache (0.2.0) | Direct-mapped, 8-byte lines, `ICACHE_BEATS` lines, store-coherent | Fetch was more than half of all clocks |
| Multiply and divide (0.4.0) | Multiply in two clocks since 0.7.1 (operands registered in EXECUTE, product in a MULTIPLY state; one clock in 0.4.0 to 0.7.0); divide and remainder by shift-subtract from the quotient's highest bit, one step per clock in a DIVIDE state | Dhrystone's one software divide per run cost about 36 instructions |
| Dual issue (0.5.0) | Second simple integer instruction from the same 8-byte beat retires in the same clock through a second retirement port | The core had reached one instruction per clock |
| B extension (0.6.0) | Zba, Zbb and Zbs in both issue slots, from one shared function | Required by RVA23; `orc.b` speeds word-at-a-time string code |
| Out-of-order implementation (0.9.0) | `rv64_ooo.sv`: rename onto 64 physical registers, 32-entry reorder buffer, 8-entry issue queue, integer and load/store ports, stores at retirement | High IPC comes from keeping execution units busy across dependencies and latencies, not from a wider single-clock datapath |
| Pipelined implementation (0.8.0) | `rv64_pipe.sv`: four stages, single issue, BTB and return stack, block-RAM-style caches, LUT-RAM-friendly register file | The multicycle core's longest path ran through most of the machine in one clock; a pipeline trades clocks per instruction for clock rate |
| Third issue slot (0.7.0) | Simple integer or B instruction after the pair, forwarding only from the first slot | Two-wide issue was close to its floor |
| Data cache (0.3.0) | Direct-mapped, write-through, no store allocation, 8-byte lines, `DCACHE_BEATS` lines | Loads waited a clock for the synchronous RAM |
| Instruction alignment | 32 bits until C arrives | Explicitly trap taken misaligned branches/jumps |
| Data alignment | Naturally aligned accesses; misalignment traps | Keeps first LSU bounded; must change for RVA23's specified main-memory behavior |
| Trap handling | Sticky external record and halt until reset | Laboratory EEI; no implicit software handler or hidden emulation |
| First SoC memory | 16 KiB single-clock synchronous RAM | No DDR controller, PCIe endpoint or cache-coherence dependency |
| Initial clock goal | Start board timing experiments at 50 MHz | A synthesis target only; no measured Fmax claim |

[RV64 integer semantics](https://github.com/riscv/riscv-isa-manual/blob/main/src/unpriv/rv64.adoc) build on [base instruction semantics](https://github.com/riscv/riscv-isa-manual/blob/main/src/unpriv/rv32.adoc). Word results sign-extend bit 31; LUI sign-extends its 32-bit result; 64-bit shifts use six count bits, word shifts five. Tests exercise those differences.

## 2. Datapath and control

```text
 PC -> aligned instruction read -> instruction register -> decode
                                                      |
                                 x-registers -> integer ALU
                                                      |
                        +-----------------------------+----------------+
                        |                             |                |
                   register result               next PC       load/store request
                        |                             |                |
                        +------- retire once ---------+         unified memory port
                                                                      |
                                                         synchronous RAM / later bus

 Any fault -> precise external trap record -> HALTED
```

States are FETCH, EXECUTE, MEMORY and HALTED, plus DIVIDE (since 0.4.0) and MULTIPLY (since 0.7.1). Instruction fetch and data accesses use the same bus. Fetch holds its request until completion, then captures the selected 32-bit half of the 64-bit response. Since 0.2.0 every fetched beat also goes into a direct-mapped instruction cache of `ICACHE_BEATS` 8-byte lines (default 512, 4 KiB; a power of two of at least 2, checked at elaboration). When the next instruction hits, the core goes straight to EXECUTE without a bus request. Reset and `fence.i` clear the whole cache and a successful store clears the line holding its beat, so fetched instructions always reflect completed stores, as before. The hit check reads the cache with the just-computed next PC; its timing cost must be checked at synthesis. EXECUTE decodes and either retires a non-memory instruction, records a memory operation, or faults. Since 0.5.0 EXECUTE can also complete the next instruction in the same 8-byte beat in the same clock: it must be a simple integer operation (OP, OP-IMM, their word forms, LUI or AUIPC), must not read or overwrite the register the first instruction writes, and the first must finish that clock (an integer operation other than a divide or, since 0.7.1, a multiply, a load that hits the data cache, or a store to a different beat). Since 0.5.1 the second instruction may come from the next beat when it is cached and may be a conditional branch with an aligned target; since 0.5.2 it may be an aligned load that hits the data cache, through a second read port, when the first is not a store to the same beat. Since 0.5.3 the first may also be a conditional branch that is not taken, and the second may be a JAL or JALR with an aligned target. Since 0.5.4 the second may be an aligned store when the first does not use the bus; if the bus stalls, the first retires and the store waits in MEMORY with its request held, and a bus error traps precisely at the store. Also since 0.5.4 an integer result of the first (not a load or multiply) is forwarded to the second's operands in the same clock, which chains two ALUs in one clock; its timing cost must be checked at synthesis. Since 0.5.5, when the first is a jump or a taken branch, the second slot executes the instruction at its target, read from the instruction cache in the same clock, and JAL/JALR links are forwarded; this adds the branch decision, the target addition and a cache read to the same clock. Since 0.7.0 a third instruction, the one after the second slot's, can complete in the same clock when it is a simple integer or B operation read from the instruction cache, does not depend on the second slot (it may use the first slot's forwarded result), and the second slot is neither a store nor a control transfer; it retires through a third set of ports (`retire3_*`) after the second. Since 0.3.0 a direct-mapped, write-through data cache of `DCACHE_BEATS` 8-byte lines (default 512, 4 KiB) serves loads: a successful load fills its line, a successful store updates a line that holds its beat (no allocation on stores), and a load that hits completes in EXECUTE with no bus request. Since 0.2.1 a load or store puts its request on the bus during EXECUTE, as soon as its address is known and no exception is pending; if the bus completes in that clock the instruction retires from EXECUTE, otherwise MEMORY holds the identical request until completion. MEMORY waits for exactly one completion and only then retires a successful load/store. Since 0.7.1 a multiply registers its operands in EXECUTE and retires from a MULTIPLY state one clock later, so the multiplier starts at flip-flops instead of following register read and decode in the same clock; a multiply never pairs. HALTED issues nothing.

Since 0.8.0 there is a second implementation of the same contract, `rtl/cpu/rv64_pipe.sv`, a four-stage single-issue pipeline with the same module name, parameters and ports (a build uses one of the two files; `--core pipe` selects it in the regression, the B cross-check and the benchmark runner). F reads the instruction cache through a register (block-RAM style) and fills it from the bus; a 256-entry branch target buffer (10-bit partial tags, 2-bit counters, target bits 31:2) and a 4-entry return-address stack updated in D predict the next fetch. D reads the register file (no reset loop, so it can be LUT RAM; a sequencer writes zero to every register in the 32 clocks after reset, before the first fetch) and redirects fetch for a JAL or backward branch the buffer did not predict. E executes, with results forwarded from M's integer result and from the last retired instruction; a mispredicted transfer redirects fetch and discards the two younger instructions. M reads the data cache through a register, performs the bus access, retires one instruction and writes the register file; multiply and divide operands are registered as they enter M. A load, multiply or divide result used by the next instruction costs one clock, except store data, which is taken in M. Differences visible at the bus: instruction fetches are issued ahead on predicted paths and may be discarded, including fetches outside memory, whose errors trap only if that instruction reaches M; a presented request is still held until it completes, and there is still one request at a time, with data accesses before new fetches. A store to the 8-byte beat of an already-fetched younger instruction, and `fence.i`, discard the younger instructions and refetch, so fetched instructions still reflect completed stores. Since 0.8.1 a 4-entry fetch queue decouples F from the rest of the pipeline, the return stack is updated in F, D checks fetch's prediction against the JAL or branch target it computes and redirects once on a mismatch, E checks only a conditional branch's direction and a JALR's target, and a bus access that does not complete in M's first clock moves to an X stage that holds the request and retires it, so no stage waits on the data-cache hit of the same clock; a new fetch waits while M holds a load or store. Traps are taken in M once no fetch is outstanding; no request follows the trap record. The `retire2_*` and `retire3_*` ports stay 0, and the visualizer state labels describe what M or F waits for.

Since 0.9.0 there is a third implementation, `rtl/cpu/rv64_ooo.sv` (`--core ooo`), an out-of-order core after the principles of large out-of-order designs, scaled to an FPGA. Its front end is the pipelined core's (F with the BTB and return stack, the fetch queue, D's prediction check). D renames one instruction per clock onto 64 physical registers (physical register 0 is x0) through a speculative map, and dispatches it into a 32-entry reorder buffer and an 8-entry issue queue. Wakeup and select issue up to two instructions per clock, one to the integer port (with a multiply/divide unit behind it) and one to the load/store port. The integer port reads the physical registers in the clock after select, so a dependent integer instruction issues in the next clock. The load/store port computes the address and reads the data cache, then checks the tag; a miss reads the bus, holding the request until it completes even if the load is discarded meanwhile. A store records its address and data and writes the bus when it retires, so traps, the trace and the write's visibility stay in program order; until 0.9.1 a load issued only when every older store had retired; since 0.9.1 it issues once every older store has its address and data, takes the data of the youngest older store to its 8-byte beat if that store covers all its bytes, and otherwise (partial overlap) waits for those stores to retire and reads the bus. The reorder buffer retires one instruction per clock in program order; register and memory state change only there. A mispredicted branch or JALR redirects fetch when it executes (if no older mispredict is waiting); rename waits until it retires, then the younger instructions are discarded and the map is restored from the retirement map. A retiring store to the beat of any younger fetched instruction, and `fence.i`, discard and refetch everything younger. Traps are taken at the head once no fetch or load request is outstanding. Since 0.9.2 the out-of-order core is two-wide: F delivers up to two instructions from an aligned beat (a second BTB lookup; not after a predicted-taken transfer, a call or a return), an 8-entry fetch queue feeds two D slots that each check their prediction, two instructions are renamed per clock (the second may read what the first writes), a second integer port executes simple integer and B operations, memory instructions issue in program order on the load/store port, and up to two instructions retire per clock (the second through `retire2_*`, never a store, `fence.i`, mispredicted branch or trap, and not two control transfers at once). Since 0.9.3 a store issues once its address is known and reads its data register when it retires (forwarding to a younger load waits until that register is written), and a retiring store writes the bus at once while its data-cache update and instruction-cache invalidation follow one clock later from a pending-update register (loads reading that line merge the pending bytes; fetch treats that index as a miss for that clock). Since 0.9.4 fetch reads the beat after the fetch beat in the same clock, so two instructions come from either half of a beat. Since 0.10.0 `rv64_ooo.sv` is a wide behavioural model configured after measurements of the Apple M5 performance core (independent microbenchmarks, useless-husband/m5-uarch): up to 8 instructions per clock are fetched (from the instruction cache, ending at a predicted-taken transfer, a call or a return), renamed and retired; a 128-entry reorder buffer, 160 physical registers and a 64-entry issue queue; 8 integer ALUs, 3 of which also execute branches, jumps, system instructions and multiply/divide (multiply 3 clocks pipelined, divide 7 clocks, one unit); 3 load ports and 2 store-address ports, selected oldest first. A load issues once every older store has its address; it forwards from the youngest older store to its beat that covers all its bytes and whose data is written, otherwise reads the data cache or a one-entry fill buffer, and replays from the issue queue when it cannot answer (cache miss, data not written, partial overlap), so a waiting load never blocks a port; the miss unit serves the oldest missing load and reserves the fill buffer for it until it completes. Each branch and JALR saves the rename map and the return-stack pointer, so a mispredict recovers in the clock it executes. Stores write the bus when they retire, one per clock, and update the write-through data cache, the fill buffer and the instruction cache. Its default caches are 128 KiB each; the regression (`tb_core.sv`) and the benchmark SoC pass 512 beats, so measured runs use 4 KiB caches. Since 0.10.1 a fetch group continues past the first predicted-taken branch or jump to its target and ends at the second, and holds at most one call or return (the M5 sustains two taken branches per clock). Since 0.11.0 a loop predictor (256 entries) learns, for each conditional branch, how many times its usual direction repeats before one opposite outcome, and predicts the exit once that count has repeated twice; an instance's iteration number comes from the youngest earlier instance still in flight, so discarded paths need no repair. Since 0.11.0 (corrections from an independent review): a failed fill reports its access fault only to the load that asked for it; a load takes each byte from the youngest older store that writes it and the rest from the cache or fill buffer, and completes only after its beat has been read successfully (a fully forwarded load gives its value to consumers at once but does not finish until that read), so forwarding cannot hide a read access fault; a load issues only after every older `FENCE` has retired; retirement outputs pulse once in a halting clock; a dependent instruction issues 3 clocks after a multiply and 7 after a divide (before, 2 and 6); the return-stack pointer (not its overwritten entries) is restored after a rename-stage redirect and a retirement flush; `RW` outside 3 to 8 stops elaboration. The data cache is two-way set associative with the same total size (the line not filled last is replaced), and stores pair on the bus as described in section 3. Since 0.11.1 a load, multiply or divide whose last 8 results at its PC were equal gives that value to its consumers at rename (value prediction, 256 entries); its own result is compared when it executes, and a wrong guess retires the instruction with its real result and refetches everything after it. Fetch also predecodes what it fetches: a direct jump or call goes to its target, a return to the return stack, and a conditional branch missing in the BTB is predicted taken when it jumps backward, so rename's prediction check (which now trusts fetch for conditional branches) no longer redirects for these. Also since 0.11.1 (second review): an instruction fetch held across a redirect cannot report its access fault to the redirected fetch of the same beat, and the loop predictor ignores branches whose run length reached its 255 limit. Also since 0.11.1 (memory agent): a load wakes its consumers when it issues, and puts its register back to not ready if it then cannot answer (issue rechecks sources); a load may issue before older stores know their addresses unless a 256-entry load-wait table, indexed by the load's PC, says it conflicted before; a store that computes its address marks every younger load that already took a value from bytes it writes, and a marked load flushes at the head and refetches from itself, setting its table entry; and retirement continues past the clock's store write up to the next store or an instruction fetched from a beat written this clock. Since 0.11.2 a simple integer instruction and the next instruction of the same rename group that reads its result are fused: the consumer may issue once the producer's sources are ready and computes the producer's value itself (until the producer has written it), as a macro-op would (instruction fusion after Condor's Cuzco core, SC25); the loop predictor and the BTB have 1024 entries each (256 before), and a conditional branch that has gone one way at least 4 times with no exit learned is predicted that way at fetch. Since 0.12.0 the default width is 16 instructions per clock through fetch, rename and retirement (`RW` 16; wider than the M5's measured 10 and than any shipping core known to us), with a 256-entry reorder buffer, 288 physical registers and a 128-entry issue queue; execution resources are unchanged. The wide trace has `RW` slots and `tb_core.sv` sets `RW` 16. Since 0.12.1 the store-write scan and retirement share one stop rule: a wrong value prediction or `fence.i` ends both (since 0.11.1 a store behind a wrongly value-predicted load could be written on the bus without retiring); and a load whose bytes came from a younger, already resolved store is no longer flushed when an older store to those bytes resolves. Since 0.12.2 (frontend engineer) a fetch group may follow up to 4 predicted-taken transfers and hold up to 4 calls and returns, with a group-local copy of the return stack (two taken and one call or return before). Since 0.12.3 (middle engineer) rename folds simple instructions: a rename-map entry is a physical register plus a 64-bit offset, so `addi` (with `mv`, `li` and `nop`), `lui`, `auipc`, `jal` with an aligned target and `jalr` whose base is a known constant finish at rename without an issue-queue entry, an execution port or a new physical register (shared physical registers are reference counted); loads and stores add the offset in address generation, other consumers of a register with a non-zero offset issue one clock later, and folded instructions retire in order with their values in the trace. Since 0.13.0 (memory engineer) store-address ports execute before load ports within a clock, and a store write request may carry up to four stores (`EXTRA_WRITES` 2, section 3). Four 8-byte writes per clock into one RAM is a behavioural assumption: hardware needs banked or multi-ported memory, or line-level store coalescing. Since 0.13.1 (backend and memory engineers) the core has 4 load ports and 3 store-address ports (3 and 2 before; Zen 5 executes 4 loads per clock and Lion Cove has 3 store-address ports). Since 0.14.0 (middle engineer) the reorder buffer has 512 entries (544 physical registers) and retirement is 32 instructions per clock (`RW` 32; fetch and rename stay 16), so the wide trace has 32 slots and `tb_core.sv` sets `RW` 32. Since 0.14.1 (frontend engineer) fetch and rename are 32 instructions per clock, a width separate from retirement, with a 64-entry fetch queue. Since 0.14.2 (fixes from a Codex review): `EXTRA_WRITES` outside 0 to 2, or non-zero without `PAIR_WRITES`, stops elaboration; a load flushed for a memory-order violation restores the return-stack pointer from its own entry; and only a load that actually delivered read or forwarded bytes (not a value prediction) can be marked as violating. Since 0.14.3 (middle engineer) rename also computes simple integer operations whose inputs are known constants (one ALU level per rename clock) and decides conditional branches whose operands are known there (the same physical register with known offsets, or two constants); such instructions need no issue-queue entry or port. It models instruction-level behaviour and cycle counts only; area and clock rate on an FPGA are not yet considered.

Register and next-PC updates happen at retirement. A faulting instruction does not retire or update its destination register. Stores become visible through the memory adapter's successful completion contract; an error response must have no write side effect. The testbench separately compares committed writes and retirement events to a sequential byte-addressed model.

ALU/branch decode is combinational in revision 0. This may infer more than one physical adder or large muxes; RTL operators are not a resource report. Later timing measurements may justify explicit resource sharing or extra execution states. Register-file reset is acceptable for this small prototype but has fanout and inference costs. RAM is not reset in a loop.

## 3. Memory interface contract

| Signal | Meaning |
|---|---|
| `mem_valid` | Request exists; remain asserted until completion |
| `mem_ready` | Request completes at this rising edge when valid is also 1 |
| `mem_instr` | Instruction fetch; otherwise data access |
| `mem_addr[63:0]` | Byte address aligned down to 8 bytes |
| `mem_wstrb[7:0]` | Zero for reads; set lane i to write byte i |
| `mem_wdata[63:0]` | Store data shifted into addressed byte lanes |
| `mem_rdata[63:0]` | Entire aligned 64-bit read beat, stable at completion |
| `mem_error` | Fault indication sampled only at completion; no store side effect |
| `mem_addr2`, `mem_wdata2`, `mem_wstrb2[7:0]` | Since 0.11.0, out-of-order core with `PAIR_WRITES`: a second store write carried by the same store request (`mem_wstrb2` zero: none) |
| `mem_error2` | Fault indication for the second write, sampled at the same completion |
| `mem_xaddr[127:0]`, `mem_xwdata[127:0]`, `mem_xwstrb[15:0]`, `mem_xerror[1:0]` | Since 0.13.0, out-of-order core with `EXTRA_WRITES` 2: a third and fourth store write in lanes 0 and 1, each applied only if every earlier write of the request succeeded, with its own fault bit |

Since 0.11.0 the out-of-order core can pair two stores in one write request when its `PAIR_WRITES` parameter is 1 (the sample SoC and `tb_core.sv` set it in out-of-order builds, `WIDE_TRACE`). The memory applies the second write only if the first succeeds, both complete at the same `mem_ready`, and `mem_error2` reports the second; the second store is the next younger store, and no instruction between the two lies in the first store's beat. A failed first write retires neither store; a failed second write retires the first and traps at the second, so store faults stay precise. With `PAIR_WRITES` 0 the second-write outputs are zero and `mem_error2` is ignored. All request fields remain stable under backpressure. A successful handshake represents one access, never one access per cycle while valid is high. The bus adapter owns address decoding, permissions, access width/PMA restrictions and any timeout. There is no silent core timeout that discards an outstanding transaction. An absent response stalls until a coordinated fabric reset or an adapter-reported error.

Since 0.3.0 the core treats every address as cacheable: a load that hits the data cache, and an instruction that hits the instruction cache, makes no bus request. Before any memory-mapped peripheral is added, a PMA mechanism must mark its region uncacheable. The current wrapper has one readable/writable/executable region 0x0000..0x3fff. Everything else returns an access fault. It performs no address truncation before the range check. Instruction fetch reads an entire aligned 8-byte RAM beat; a later MMIO/PMA adapter must not turn this into an over-wide side-effecting peripheral read. Vector, cache and bus adapters will need explicit access-size and attribute metadata before general platform integration.

Reset is synchronous and must reset/quiesce the core and its memory adapter together. The dedicated reset test cancels a store **before acknowledgement** in that shared-reset environment. It does not establish rollback of completed stores, safe cancellation of AXI/PCIe writes, or permission to reset a live external fabric independently. Later system-reset logic must drain or isolate outstanding external accesses.

The sample SoC uses byte write enables and a synchronous read. Since 0.2.2 it acknowledges a write in the clock the request is presented, writing on that clock edge, with the out-of-range error decided combinationally; reads still answer one clock later. `RAM_WORDS` must be a power of two >=2; default 2048. Hex initialization has 2048 lines of 16 hexadecimal digits, each a little-endian 64-bit memory word. The RAM wrapper is simulation-tested, but actual BRAM inference and read/write behavior must be checked in the selected FPGA tool.

## 4. Trap and retirement contract

`trap_valid` remains set until reset; `trap_pc`, `trap_cause`, `trap_tval` remain stable. Causes use standard exception numbers for diagnostics:

| Cause | Revision 0 behavior |
|---:|---|
| 0 | Misaligned instruction target; tval=bad target; a not-taken branch does not fault |
| 1 | Instruction bus/access fault; tval=current PC |
| 2 | Unsupported/illegal instruction; tval=32-bit instruction zero-extended |
| 3 | EBREAK; tval=0 |
| 4 /5 | Misaligned load / load access fault; tval=effective byte address |
| 6 /7 | Misaligned store / store access fault; tval=effective byte address |
| 11 | ECALL from this laboratory M-origin environment; tval=0 |

The processor does not yet implement architectural machine mode just because it emits cause 11. The next stage replaces terminal reporting with a real CSR/privilege/trap implementation and a firmware handler. Unknown CSRs currently cause illegal instruction. FENCE is satisfied by the serial memory model; FENCE.I is satisfied by completing stores before a new, uncached instruction fetch. Self-modifying code is tested.

Retirement exports PC, instruction, destination/data and successor PC with a one-cycle valid pulse. Since 0.5.0 a second set of ports (`retire2_*`) reports a second instruction retired in the same clock; it always follows the first in program order, so a trace that logs slot one and then slot two is the sequential order. Since 0.7.0 a third set (`retire3_*`) follows the second in the same way. Since 0.10.0 the out-of-order core also exports a wide trace, `rt_valid`, `rt_pc`, `rt_insn`, `rt_rd`, `rt_data` and `rt_next` (parameter `RW`, default 8 slots, 16 since 0.12.0, 32 since 0.14.0, slot 0 oldest, slots filled from 0 without gaps), and `retire_*` to `retire3_*` repeat its first three slots. A store's write is logged immediately before that store's own retirement, in whichever slot it retires; at most one store retires per clock, two since 0.11.0 when a write request carries a pair (section 3). Destination zero denotes no architectural register write and reports data 0. This is useful debug visibility, not the full RVFI formal interface. Add memory, privilege and trap fields needed by an external architectural checker without changing commit order. [Machine-level reference](https://github.com/riscv/riscv-isa-manual/blob/main/src/priv/machine.adoc).

## 5. RVA23 completion ledger

The following covers every mandatory entry named in RVA23U64. Entries group related requirements, not implementation claims. Consult the linked specification for their exact semantics and dependencies.

| B | Implemented in 0.6.0 (Zba, Zbb, Zbs); local tests and a compiler cross-check pass | C2 external-model comparison |

Zfbfmin, Zvfbfmin and Zvfbfwma are optional BF16 additions worth considering for the later LLM workload. They cannot replace required D or the complete V behavior. Likewise, executing the previous assembly examples is an integration test, not profile certification.

| Gate | Deliverable | Required exit evidence |
|---|---|---|
| C0: working integer foundation | Current multicycle core, RAM, firmware and local tests | Directed/random instruction traces, memory lanes, faults, backpressure, reset and self-modifying fetch; local results recorded |

| C4: scalar floating point | F/D, conversions, FP16-minimal, Zfa, fcsr | Independent IEEE results including NaN boxing, signed zero, subnormal, rounding modes, exception flags and arithmetic corner cases; no silent FTZ |

| C6: profile/platform closure | User environment, pointer masking, cache-block/PMA behavior, remaining counters and data-independent-latency requirements | Versioned ISA/PMA manifest; relevant architectural suite; privilege and environment tests; no missing mandatory item hidden as software support |
| C7: FPGA proof | Exact FPGA part, clocks, reset synchronizer, constraints, memory adapter and firmware path | Synthesis/inference, timing, CDC/reset checks, resource/thermal/power evidence, actual programmed board result |

Physical C7 work can begin on the C0 core before the full profile is complete. Label that bitstream by its implemented ISA. Keep long-operation units behind explicit start/busy/done/error interfaces and retire only after completion. Preserve precise exceptions when adding iterative divide or FP operations.

The initial vector architecture is a **proposal**, not implemented RTL: VLEN128 gives32 x128=4096 architectural register bits, with banked synchronous storage; execution can process fewer elements per cycle. A small implementation still needs FP64, legal element widths/groups, masks/tails and complete memory/restart semantics. A BF16-only vector MAC would be a workload accelerator, not V compliance. [V requirements](https://github.com/riscv/riscv-isa-manual/blob/main/src/unpriv/v-st-ext.adoc).

Supervisor/Linux work requires a separate platform design. Full RVA23S64 additionally includes Ss1p13, Svbare/Sv39/Svade, translation and memory-type extensions, supervisor timers/counters/pointer masking, and Sha with hypervisor-related requirements. Do not quietly rename an Sv39 Linux experiment as complete RVA23S64.

## 7. FPGA budget and measurement plan

Known architectural storage now: 2048 register bits, plus PC/instruction/LSU/control state; example RAM 131072 bits. That is a storage inventory, not an inferred FF/LUT/BRAM count. Shift networks, register muxes, ALU carry chains and reset choices need synthesis. The old accelerator resource spreadsheet cannot predict these costs.

Keep revision 0 vendor-independent. Before buying a board, synthesize the standalone core and RAM wrapper for candidate exact parts, report utilization with and without debug traces, inspect RAM inference, and constrain a real board clock. Start timing experiments at 50 MHz, then record achieved timing rather than adopting an unsupported frequency. Choose BRAM/programming access and usable free tool support before LUT count alone. The earlier [board analysis](../fpga-resource-and-board-analysis.md) supplies dated research, not a refreshed CPU recommendation.

Free work today uses the existing ARM workstation, LLVM cross compilation and Ubuntu Icarus. Yosys/Verilator were not on the inspected WSL PATH; no synthesis run is claimed. The previously documented supported x86-64 Vivado-host requirement still matters for an AMD hardware route.

## 8. Evidence and limitations

Recorded expanded run on version 0.4.0: 37 programs under zero, up-to-7 and up-to-19 response wait cycles; 111 differential runs; 66 instruction names covered, including divide by zero and signed overflow, every branch outcome, memory widths/lanes, invalid encodings, misaligned and unmapped accesses, injected instruction/load/store faults, x0 behavior and ordered retirement. Separate reset and RAM-wrapper checks pass. Compiled C produces 36 and 0x000000240000007e through the actual synchronous wrapper.

The reference model was written separately as a sequential byte-memory interpreter, but remains project code and can share conceptual mistakes. External Sail/Spike comparison, official architectural tests, formal proofs, privileged behavior, independent review, synthesis and physical timing remain pending. The infographic is an educational state animation; it is not a live RTL waveform or a performance estimate.

## 9. Versioning

The CPU architecture has one [semantic version](https://semver.org/), `MAJOR.MINOR.PATCH`. It is stored in [VERSION](VERSION) and in this document's title, and the repository check fails if the two differ. Benchmark results and rubric scorecards record it.

### What the version covers

The version tracks the architectural contract that software, adapters and testbenches rely on:

- the implemented ISA string and the semantics of every implemented instruction;
- the execution environment: trap causes, the trap record, privilege modes and CSRs;
- the ports of `rv64_core` and `rv64_bram_soc`, the memory-bus handshake and the retirement trace;
- parameters and their defaults, the reset PC and the sample SoC's memory map;
- documented behavior others may depend on, such as one outstanding memory request.

It does not cover tests, testbenches, tools, benchmarks or documentation wording. The preserved accelerator design keeps its own ABI and adapter version numbers.

### Which number changes

From 1.0.0 onward:

| Bump | When | Examples |
|---|---|---|
| MAJOR | Incompatible change to the contract | Removing or renaming a port; changing the bus handshake; changing a trap cause or the trap record's meaning; changing a parameter default; removing an instruction |
| MINOR | Backward-compatible addition | Adding Zicsr, M or C; a new port or parameter whose default keeps existing behavior; new trap causes for a new feature |
| PATCH | RTL change with no contract change | A bug fix that restores documented behavior; timing, area or clocks-per-instruction improvements with identical architectural behavior |

A bug fix that changes behavior software may already rely on counts as incompatible. Documentation corrections that do not change the contract need no bump.

Before 1.0.0, anything may change (semantic versioning, item 4). This project then bumps MINOR for any contract change, breaking or additive, and PATCH for any other RTL change, and marks every breaking change in the history below.

Proposed criteria for 1.0.0, when the core and bus interfaces are frozen: C1 complete, an external-model comparison in the regression (rubric HG3), and a first exact-part synthesis. Changing these criteria is itself recorded here.

### Releasing a version

For every change to `rtl/cpu/` or to the contract in this document:

1. Decide the bump from the table. A change to tests or wording only needs none.
2. Update [VERSION](VERSION) and this document's title together.
3. Add a row to the history: version, date, commit, summary, whether it breaks compatibility, and the short RTL hashes.
4. After the change lands on `main`, tag that commit `cpu-vX.Y.Z` with an annotated tag.
5. Record the release in [DEVLOG.md](../DEVLOG.md). If the RTL changed, rerun the regression and Dhrystone and reassess [rubric-evidence.json](rubric-evidence.json).

Once Zicsr arrives in C1, consider reporting the version in the implementation-defined `mimpid` CSR so software can read it.
