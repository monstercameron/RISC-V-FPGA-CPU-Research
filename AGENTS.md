# Repository guidance

- Start with README.md and cpu/architecture.md. The user changed the active priority to CPU CORE FIRST on October 23, 2026: an original FPGA RV64 core with a staged RVA23U64 target. The LLM accelerator documents are preserved research/future work.
- CPU behavior is governed by cpu/architecture.md. Run sim/cpu/run.sh for RTL changes. Keep ISA/profile, privilege, simulation and physical-hardware claims distinct. For accelerator changes, read its implementation, ABI and adapter contracts first.
- Root plans/helpers are maintained. Files in llm-accelerator/planning-evidence/ are historical snapshots; avoid changing duplicate copies casually.
- The CPU architecture uses semantic versioning (cpu/architecture.md section 9; current version in cpu/VERSION). Every change to rtl/cpu/ or to the architectural contract must decide its bump (MAJOR, MINOR, PATCH, or none for test and wording changes), update cpu/VERSION and the architecture title together, add a history row, and be tagged `cpu-vX.Y.Z` once on main. Never reuse or move a released version number.
- Version each change on its own. Integrate one hand-off or fix at a time, each as its own semver step with its own commit, `cpu-vX.Y.Z` tag, history row and DEVLOG.md entries. Each step needs a regression at both cache sizes and probe or logged Dhrystone numbers. The history then shows the evolution step by step and every gain stays attributable. Never bundle several improvements into one version. A bug fix is a PATCH, a contract change is a MINOR, and a microarchitectural change that keeps the contract is a PATCH.
- Preserve exact bytes and upstream headers in reference-sources/, source/fixture locks and vendored code. Intentional identity changes need provenance, a versioned reason and independent review; never regenerate anchors solely to silence a failure.
- Document every experiment in DEVLOG.md during the session in which it happens, and read the latest entry before starting work. An experiment is any run that produces evidence or tests an idea: simulations and regressions, benchmarks, synthesis or timing runs, board tests, tool installs or upgrades, and trials that failed or were abandoned. Each record gives the time and its source, the goal, the exact commands, tool and compiler versions, the commit hash or "uncommitted", results with units, and the conclusion. Record failures and surprises as well as passes. Add to the log; do not rewrite earlier entries except to correct a fact, and say when you do.
- DEVLOG.md holds daily summaries, commit messages, findings and an index of runs. Bulky per-run detail goes in `devlog/devlog-<commit>.md`, one file per commit that was checked out, so DEVLOG.md stays small. Every Dhrystone run writes its result, rubric scorecard and trace profile there and adds an index row to DEVLOG.md. `sim/cpu/bench/run_dhrystone.ps1` does this by default; when running `run_bench.py` directly, pass `--devlog`. Keep `cpu/rubric-evidence.json` current: reassess it whenever evidence changes or the RTL hashes change, because a stale assessment zeroes the R1-R6 scores. A scorecard is a self-assessment and never replaces an independent review.
- When a second opinion is needed (a risky RTL change, a contract change, a surprising result), spawn a Codex CLI subagent running GPT 6.2 Astra (the model the user named) to review the work adversarially. The CLI comes with the ChatGPT/Codex desktop app (`%LOCALAPPDATA%\OpenAI\Codex\bin\<build>\codex.exe`; `~/.codex/config.toml` sets `gpt-6.2-astra`). Run it non-interactively and read-only, for example `codex exec -s read-only -C <repo> -`, with the prompt on stdin. Give it the diff and the files to read, not your conclusion, and ask it to find bugs and unsupported claims. Record its findings, and what you did about each, in DEVLOG.md. Its review is a second opinion. It does not replace an independent human review.
- While the core is being optimized, run that Codex reviewer (GPT 6.2 Astra) every 15 minutes. Each time, have it review the project read-only and suggest feasible enhancements and bugs toward the current goal, 20 DMIPS/MHz on Dhrystone. Its suggestions go to the coordinator, who reviews each one, assigns or rejects it with a reason, and logs the decisions in DEVLOG.md.
- During long working sessions, the coordinator gives the user a short status update about every 5 minutes. Each update covers what each agent is doing, the latest measured numbers against the goal, what is running and whether anything is blocked. Get the time from the clock, and never let a long run go quiet.
- Keep the GitHub Pages site in `docs/` current. At the end of every successful logged run of a new CPU version, add that version to the gallery and bring the journal up to date with DEVLOG.md, in the same change as the version's commit. For a new version, add a work entry to the `WORKS` list in `scripts/build_site.py`: a title, a caption and a drawing spec after its history row. Then run `python -B scripts/build_site.py` and check the gallery and journal pages. The site only counts as published once main is pushed and Pages serves `/docs`.
- Run `python -B scripts/check_repo.py` for applicable repository/planning changes. Run focused RTL/numerical checks when their implementation changes. Record unavailable empirical validation accurately.
- Keep generated files in build/ or another ignored directory. Do not download model weights or start long native runs without the plan's storage/RAM/runtime admission checks.
- Keep MIT original-work licensing separate from third-party terms. Add provenance/license notices when importing material.
- Do not invent repository owners, private contacts, CI results, releases or measured hardware performance. Changes to a previously reviewed artifact do not inherit its old review score automatically.
