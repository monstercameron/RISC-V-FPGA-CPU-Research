# Adapter protocol 1: session, uploads and streamed weights

Normative companion to [ABI 1](abi-v1.md). This specifies the adapter that a board-specific RTL/driver pair must implement, not an assertion that LitePCIe already provides it. The graph sequencer, positions and all numerical operations remain on-core. The host services immutable byte ranges and transport only. Simulation must implement these same handshakes against byte-addressed backing stores.

## Session initialization and fixed register extensions

The ABI register window is at least4KiB, little-endian. Add these offsets to ABI1's original map:

| Offset | Bytes | Function |
|---|---:|---|
| 0x610 | 4 | Adapter protocol version, read-only, value1 |
| 0x640 | 16 | Host-proposed session nonce, write while uninitialized only |
| 0x680 | 8 | Region handle for SEAL |
| 0x700 | 64 | Device weight-range request, read-only while REQUEST_VALID |
| 0x740 | 32 | Host weight-range response |
| 0x760 | 4 | Weight service status: bit0 REQUEST_VALID, bit1 RESPONSE_READY, bits4..5 stageA state, bits6..7 stageB state; rest0 |
| 0x800 | 64 | Host adapter-copy descriptor |
| 0x840 | 64 | Adapter-copy completion |

Doorbell0x600 additional single values: 8 INIT_SESSION,16 ADAPTER_COPY,32 SEAL,64 WEIGHT_RESPONSE. Do not combine flags in a doorbell write. Status0x604 adds bit7 SESSION_READY, bit8 COPY_READY, bit9 COPY_COMPLETION_VALID. W1C0x608 bit9 consumes copy completion. INIT and SEAL use the region acknowledgement mailbox0x540 and its existing readiness/result credits; they cannot race a region registration. INIT acknowledgement uses command-ID0, context/epoch/count0, opcode0x101; SEAL uses command-ID=region handle, owner context/epoch, opcode0x102. Both use failing layer0xffffffff, status and zero remaining fields. An illegal doorbell produces an error in the corresponding available result slot or rejects the MMIO transaction if that slot/READY is unavailable; never overwrite pending results.

Power-on/reset: SESSION_READY=0, model/context unregistered, region table empty, DMA disabled. Read-only capabilities and control QUERY_CAPS work before session init; other submissions fail BUSY. The trusted driver performs required board/link/memory tests, establishes its DMA mask/IOMMU/pin budget, writes a nonzero128-bit nonce, then rings INIT. Device latches that nonce into capability bytes192..207, enables registered-only copy service and acknowledges success. Reinitialization without a positively quiescent full device reset is rejected. Nonce does not authorize raw DMA; kernel ownership and region checks do. No capability field is secretly writable. Initial model/layout digests are zero until REGISTER_MODEL succeeds; numerical kernel/constants/config capabilities reflect the supported bitstream profile.

## Initial DDR upload and descriptor sealing

Region permissions extend bit0 READ/bit1 WRITE with bit2 INIT_WRITE. Legal values are1,2,3 and5 only. Value5 means core-read plus **adapter-only initialization write**, allowed only for BOARD_DDR or simulation backing; no core write. Such a region starts UNSEALED and cannot be referenced by a command/table/weight request. Driver registers pinned HOST_DMA source segments and destination regions, uploads bytes using ADAPTER_COPY, then SEALs every input/table/constant region before use. SEAL requires idle device, zero outstanding copies/requests touching the region, correct generation and initialized extent; it atomically changes5 to1 and marks SEALED. READ-only BOARD_DDR registrations without INIT_WRITE are rejected; the simulator may supply a prevalidated sealed table backing. HOST_DMA read-only buffers and MODEL_BYTES remain valid read-only kinds. Board DDR tables cannot bypass upload/seal. Every byte in a table/input extent must be initialized; the driver tracks coverage and adapter tracks the declared completed copy ranges. Sparse uninitialized table tails are rejected.

COPY descriptor has eight u64 fields: tag@0, context ID@8, epoch@16, source handle@24, source offset@32, destination handle@40, destination offset@48, length@56. All are checked; tag nonzero monotonic per session, length1..128MiB, source/destination ends checked in u64. Allowed directions: HOST_DMA->BOARD_DDR and BOARD_DDR->HOST_DMA (SIM_MEMORY substitutes in simulation). Source must permit READ; destination WRITE or currently UNSEALED INIT_WRITE. A copy cannot read an unsealed DDR region. Context/epoch0 is for idle initialization; otherwise both match the context owning mutable ranges. Neither side may be MODEL_BYTES, whose file service is described below. Range/permission checks precede issue; copy engine splits at4KiB and DMA segment boundaries, never inventing a contiguous IOVA across handles.

COPY uses its own ready/result slot and a common64-byte completion: tag in command-ID, supplied context/epoch, committed=0, status, opcode=0x100, layer=0xffffffff, flags0, elapsed cycles and transferred-valid bytes. Success means writes are visible at the destination under the adapter's tested fence/ack contract; error bytes are0. Host release ordering precedes doorbell; acquire ordering follows completion VALID. Exactly one copy outstanding in adapter1. SG lists are **multiple copy descriptors**, each referencing one registered segment. Never reuse/unmap a source merely because bytes were submitted. Caller synchronizes host caches with its OS DMA API before/after ownership transfer.

While EVALUATE is active, ADAPTER_COPY may only fill the destination subrange of the current outstanding weight request from registered HOST_DMA source segments; no arbitrary state/table/output copy is allowed concurrently. Idle readback is allowed for output/state diagnostics. Normal numerical HOST_DMA output writes are issued by the core's registered memory adapter and obey their own completion visibility rules. Shared copy/DDR/DMA service is included in bandwidth accounting; a control mailbox is not a hidden independent data bandwidth.

## Tagged immutable weight service

REGISTER_CONTEXT's workspace manifest names two disjoint BOARD_DDR/SIM_MEMORY mutable regions `WEIGHT_STAGE_A/B`, each bounded by its registered extent (candidate128MiB each). These are additional workspace-table entries, not two hidden allocations inside the128MiB general scratch region. Staging starts FREE. Core selects a FREE stage, reserves its destination range, and publishes a request. Only one host weight request is outstanding; one other stage may be READY/IN_USE by compute. The core's on-board four read tags and small tile response credits are separate from this host-service limit.

Weight request64 bytes: tag u64@0, numerical command ID u64@8, context epoch u64@16, MODEL_BYTES source handle u64@24, logical source byte offset u64@32, stage destination handle u64@40, destination byte offset u64@48, byte count u32@56 (1..128MiB), flags u32@60=0. Context ID is resolved from the sole active numerical command. All source/destination handles include generations. Source offset is relative to its logical file region; checked base+offset selects bytes in the immutable packed payload. Device validates command/epoch, manifest tensor extent, file-region extent and stage extent before publication. Host revalidates them and serves exactly that requested byte range.

Request tags increase monotonically within the session; no wrap/reuse. Set REQUEST_VALID and RESPONSE_READY after the record is visible; it remains immutable until a matching accepted response. The host may fill any number of registered bounded host buffers from the verified file, then issue sequential COPY descriptors to contiguous parts of this reserved destination. This supports file offsets above4GiB and scatter/gather source mappings without whole-tensor residency. The byte-range service may copy or read files; it may not calculate model activations or decide graph order.

Response32 bytes: request tag u64@0, command ID u64@8, epoch u64@16, status u32@24, valid byte count u32@28. Status0 success,5 transport error,7 canceled. Success requires valid count exactly requested and all covering COPY operations successfully completed/visible; the adapter's range-coverage ledger rejects holes/overlaps and stale acknowledgements. Error/canceled requires count0. Host writes record with release ordering, rings64; acceptance atomically clears REQUEST_VALID/RESPONSE_READY. A malformed or stale response is rejected, recorded in diagnostic status, and cannot release credits or mark a stage ready. Driver must handle the outstanding valid request or terminate the device through bounded fatal recovery.

Stage state encodings:0 FREE,1 FILLING,2 READY,3 IN_USE. Request publication FREE->FILLING reserves the whole requested extent. Successful response FILLING->READY. On-core consumer start READY->IN_USE; final read completion plus consumer release IN_USE->FREE. This last transition is the explicit release event visible in service status; the host may write a stage only when a **new request** reserves it, not merely after observing FREE. Thus the host never decides when an old weight tile is dead. Double-buffer overlap is permitted only when these lifetime and memory-credit conditions hold. A stage does not hold an entire model tensor by implication.

## Cancellation, error and reset

CANCEL stops new core/host requests. A published request that has not issued any copy can receive CANCELED immediately. An in-progress service stops further copies and retains all buffers until already-issued transfers drain; only then can it return CANCELED. The numerical command's drain includes the copy engine, pending weight service, on-core tile reads, output and state writes. Canceled READY/IN_USE stages are released only after consumers and writes quiesce. Normal drain deadline is the implementation contract's five seconds; a stalled host, absent response or lost link produces OFFLINE/quarantine. Do not fake a fill completion to escape cancellation.

Any fatal result disables new copies/requests. Positive OS/adapter isolation is required before buffer unmap/reuse, even if the session nonce/epoch changes. Reset cannot clear a live request and reuse its destination. A normal successful RESET_CONTEXT follows the ABI's atomic owner-epoch rebinding rule after all services have drained; a full session reset discards metadata only after platform-confirmed quiescence. Failed reset preserves old ownership metadata and invalidates context, allowing a subsequent full clear/rebind retry only when transport is healthy.

## Mandatory integration proof

Before D4/hardware DMA enablement, run a behavioral-transport trace with the real parser/adapter: initialize nonce; register host/DDR ranges; upload/seal descriptor/input tables; register model/context; EVALUATE; serve at least two requests using alternating stages, including a logical model offset above4GiB and a source split across two noncontiguous HOST_DMA handles; compute consumption/release; output completion; reset/re-evaluate. Inject a cancellation during the second SG copy, duplicate/stale response, incomplete coverage, failed copy, missing response and failed isolation. Record tags, generations, epochs, states, range coverage and terminal results. `abi-lifecycle-example.json` defines expected contract transitions and byte fixtures; it is not this implemented integration test. No board-specific adapter qualifies by merely emitting that JSON.
